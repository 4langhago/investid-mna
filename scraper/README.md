# 실시간 매물 수집 (99.co)

## 동작 방식
```
scraper/scrape_99co.py  →  js/live_data.js (LIVE_LISTINGS)  →  db.js가 LISTINGS에 병합  →  사이트에 표시
                        →  scraper/output/live_listings.json (원본 백업)
```
- 실시간 매물은 id가 `live-` 접두사로 구분되며, 카드에 🛰️ 아이콘과 "원문 ↗" 링크(99.co 상세 페이지)가 표시됩니다.
- 실시간 매물은 localStorage에 저장되지 않고 스크래퍼 실행 시마다 통째로 교체됩니다 (어드민에서 수정해도 다음 수집 때 원복).
- 수집 0건이면 기존 live_data.js를 덮어쓰지 않고 종료합니다(안전장치).

## 실행
```
py -3 scraper/scrape_99co.py                 # 기본 7개 지역 (탕그랑, 자카르타 남부/서부, 데포, 브카시, 반둥, 수라바야)
py -3 scraper/scrape_99co.py tangerang depok # 특정 지역만 (99.co 도시 슬러그)
```
표준 라이브러리만 사용 — 별도 pip 설치 불필요.

## 자동 갱신 (Windows 작업 스케줄러)
관리자 PowerShell에서 1회 실행 (매일 07:00 수집):
```powershell
schtasks /Create /TN "MNA-99co-scraper" /SC DAILY /ST 07:00 `
  /TR "py -3 D:\0.Cursor\MNA\scraper\scrape_99co.py" /F
```
해제: `schtasks /Delete /TN "MNA-99co-scraper" /F`

## Rate Limit 주의 (완화 금지)
- 요청 간 딜레이 15초, 429 수신 시 45초 대기 후 1회 재시도.
- 2.5초 간격에서 두 번째 요청부터 429가 발생하는 것을 실측으로 확인함. 딜레이를 줄이면 IP가 장기 차단될 수 있습니다.
- 하루 1~2회 수집이면 충분합니다. 수집 주기를 분 단위로 줄이지 마세요.

### 인도웹 게시판 선정 (2026-08-11 실측)
`real_estate_mb`(28건/페이지)가 실제 매매·양도 글이 매일 올라오는 주력 게시판이고,
`biz_promo`에도 업체 양도 글이 섞여 올라옵니다. 기존 코드는 이 둘을 보지 않고
방치된 `real_estate`(4건)와 `market`만 봐서 수집이 **1건**에 그쳤습니다. 게시판을 넓히고,
당일 글의 `HH:MM` 날짜 형식을 파싱하게 고쳐 **8건**으로 늘었습니다.

상세 페이지에서 거래분류·주소·가격·건물형태·면적과 사진 URL을 함께 받아옵니다.
글쓴이 이름·전화·이메일·메신저 ID는 저장하지 않습니다(`MASK_RE`로 제거).

한인 사이트 추가 조사 결과: `haninpost.com`은 봇 요청에 응답이 끊기고,
`hankookin.com`은 본문이 비어 있는 JS 렌더링 사이트라 현재 수집 대상이 아닙니다.

## 사이트에 붙는 판정 (`enrich.py`)
예전에는 외국인 취득·운영 가능 판정을 텔레그램 발송할 때만 계산하고 버려서,
같은 매물을 사이트에서 봐도 한인이 인수할 수 있는 물건인지 알 수 없었습니다.
지금은 각 스크래퍼가 `js/*.js`를 쓰기 직전에 `enrich.annotate_all()`을 호출해
판정 결과를 매물 레코드에 남깁니다.

| 필드 | 내용 |
|---|---|
| `summaryKo` | 한글 요약 줄 목록 (`korean_brief`) |
| `foreignStatus` / `foreignReason` / `foreignSteps` | 가능·조건부·불가 + 사유 + 필요 절차 |
| `operability` / `operabilityReasons` / `operabilityTodos` | 운영가능·확인필요·부적합 + 근거 + 확인 항목 |
| `koreanEligible` | 위 둘의 결론. 사이트의 **"한인 인수 가능 매물만"** 체크박스가 이 값을 봅니다 |

`koreanEligible`은 '불가'와 '부적합'만 떨어뜨립니다. '조건부·확인필요'까지 버리면
실제로 볼 만한 물건이 거의 남지 않아서, 대신 사유와 절차를 함께 노출합니다.
판정 필드가 없는 구(舊) 수동 등록 매물은 필터에서 숨겨집니다 —
판정하지 않은 것을 가능으로 보여주면 필터의 의미가 없어지기 때문입니다.

### 부동산은 사업체와 다른 잣대로 본다 (2026-08-14)
`operability.py`의 '영업 실체' 규칙(매출·업력·직원 신호)을 부동산에도 그대로 적용하던
동안 99.co 매물 **153건 중 143건이 '부적합'**으로 떨어졌습니다. 루코 매매 글에 매출이나
직원 수가 적혀 있을 이유가 없으니 당연한 결과였고, 판정이 틀린 것이었습니다.
지금은 부동산에 대해 '실물을 특정하고 거래를 검토할 수 있는가'(가격·면적·좌표·증서 표기)를
묻는 별도 경로(`_classify_property`)를 씁니다. 같은 데이터에서 152건이 통과합니다.

## 텔레그램 추천 - 3중 스크리닝
`telegram_recommend.py`는 아래 세 관문을 모두 통과한 매물만 발송합니다.

1. **운영 가능성** (`operability.py`) 🟩 운영가능 / 🟨 확인필요 / 🟥 부적합
   — 🟥는 발송 제외. 임대 글, 구인·가맹점 모집, 거래 종료, 365일 초과 게시,
   그리고 **영업 실체 신호(영업중 여부·매출·업력·직원)가 하나도 없는 글**이 여기서 걸립니다.
2. **외국인 취득 가능성** (`foreign_eligibility.py`) 🟢 가능 / 🟡 조건부 / 🔴 불가
   — 🔴는 발송 제외(Girik 미등기 토지, 외국인 투자 유보 업종).
   `--foreign-only-eligible` 로 🟢만 받을 수 있습니다.
3. **실재성** — 필수 필드·원본 링크·플레이스홀더 연락처·단위 오기재 가격 검증.

### 메시지에 담기는 내용
- **한글 상세** (`korean_brief.py`): 개요/영업현황/인수범위/계약·비용/건물·시설/권리·인허가
  섹션으로 나눠 제시. 인니어와 한국어 원문 모두에서 추출하며, 기계 번역은 하지 않습니다.
- **법적 쟁점** (`legal_check.py`): 업종별 외국인 지분 규제, 지분·명의 구조(asset deal vs
  share deal), 그리고 **한국인 인수 건에서 반복된 사고 유형**(명의신탁 무효, 임대인 승계
  거부, 퇴직금 승계, 숨은 채무 등)을 매물 조건에 해당할 때만 붙입니다.
- **인수 후 운영 개시 절차**: PT PMA 설립 → 투자자 KITAS → 인허가 이전 → 임대차·자산 승계
  → 인력 승계 → 세무 체계까지 순서와 기간·비용 범위.
- **운영 전망·비용 구조**: 회수 기간, 인건비(UMP 기준), 임대료 구조, 업종별 비용 함정.
- **사진·지도·평판 확인 링크**: 원문 사진 URL, 구글 지도, 구글/인스타 검색 링크.
  리뷰 내용을 긁어와 요약하지는 **않습니다** — 매물명과 실제 상호가 일치한다는 보장이 없어
  엉뚱한 가게의 평점을 붙일 위험이 있기 때문입니다.
- **공적 장부 조회 링크**: AHU(법인 등기) · OSS(인허가) · BPN(토지 증서) ·
  대법원 SIPP(소송 검색) · DJP(세무).

메시지는 4096자를 넘으면 **잘리지 않고 나뉘어** 발송됩니다(예전에는 뒤쪽 내용이 잘렸습니다).

법률 자문이 아닌 공개 데이터 기반 1차 스크리닝입니다. 판정 근거가 되는 제도 요약은
`foreign_eligibility.py` / `legal_check.py` 상단 주석에 있습니다.
