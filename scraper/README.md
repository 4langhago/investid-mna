# 실시간 매물 수집 (99.co)

## 동작 방식
```
scraper/scrape_99co.py  →  js/live_data.js (LIVE_LISTINGS)  →  db.js가 LISTINGS에 병합  →  사이트에 표시
                        →  scraper/output/live_listings.json (원본 백업)
```
- 실시간 매물은 id가 `live-` 접두사로 구분되며, 카드에 🛰️ 아이콘과 "원문 ↗" 링크(99.co 상세 페이지)가 표시됩니다.
- 실시간 매물은 localStorage에 저장되지 않고 스크래퍼 실행 시마다 통째로 교체됩니다 (어드민에서 수정해도 다음 수집 때 원복).
- 수집 0건이면 기존 live_data.js를 덮어쓰지 않고 종료합니다(안전장치).

## 실행
```
py -3 scraper/scrape_99co.py                 # 기본 7개 지역 (탕그랑, 자카르타 남부/서부, 데포, 브카시, 반둥, 수라바야)
py -3 scraper/scrape_99co.py tangerang depok # 특정 지역만 (99.co 도시 슬러그)
```
표준 라이브러리만 사용 — 별도 pip 설치 불필요.

## 자동 갱신 (Windows 작업 스케줄러)
관리자 PowerShell에서 1회 실행 (매일 07:00 수집):
```powershell
schtasks /Create /TN "MNA-99co-scraper" /SC DAILY /ST 07:00 `
  /TR "py -3 D:\0.Cursor\MNA\scraper\scrape_99co.py" /F
```
해제: `schtasks /Delete /TN "MNA-99co-scraper" /F`

## Rate Limit 주의 (완화 금지)
- 요청 간 딜레이 15초, 429 수신 시 45초 대기 후 1회 재시도.
- 2.5초 간격에서 두 번째 요청부터 429가 발생하는 것을 실측으로 확인함. 딜레이를 줄이면 IP가 장기 차단될 수 있습니다.
- 하루 1~2회 수집이면 충분합니다. 수집 주기를 분 단위로 줄이지 마세요.

### SMERGERS 를 추가한 이유 (2026-09-19)
기존 C2C 소스(OLX·tempat-usaha·인도웹)에는 구조적인 구멍 세 개가 있었습니다.

1. **재무가 없다.** `omzet 15jt/bulan` 같은 매도인 한 줄이 전부라 검증할 것이 없습니다.
2. **전부 자산 양수다.** 인도네시아는 인허가(NIB·업종허가)의 법인 간 이전 제도가 없어,
   자산만 사면 인수자의 신설 PT PMA 가 허가를 **전부 새로** 받아야 합니다(그 사이 영업 공백).
   현지 M&A 가 대부분 주식 양수로 이뤄지는 이유인데, 공개 게시판에는 그 구조가 올라오지 않습니다.
3. **₩3억 이상 구간이 비어 있다.** 그 규모의 딜은 C2C 게시판에 올라오지 않습니다.
   역설적으로 PT PMA 투자계획 Rp 100억(≈₩8.6억)을 단독 충족하는 구간이 거기부터입니다.

SMERGERS 는 매출·EBITDA·자산·부채를 공개하고 지분 양도가 가능한 매물이 섞여 있어 위 셋을 메웁니다.
수집기가 **담지 않는 것**: 프랜차이즈 가맹(신규 개설), 대출 모집, 매출 Nil(비영업 법인),
자카르타·수도권 밖, 매물이 아닌 플랫폼 유도 카드.

⚠️ 이 소스에는 **게시일이 없습니다.** 대신 매도인의 최근 접속 상태(Active / Moderately Active)를
카드에 노출하므로, 게시일을 지어내지 않고 `listingActivity` 로 남기고 `business_gate` 가
그 필드로 신선도를 판정합니다(`FRESH_LISTING_ACTIVITY`).

⚠️ 제목이 정형 문구라("<업종> Company Equity Stake For Sale in Jakarta, Indonesia") 서로 다른
매물끼리 토큰이 90% 겹칩니다. `telegram_recommend.dedupe_listings` 의 제목 유사도 규칙을 그대로
대면 **47건이 1건으로 뭉개집니다**(실측). 그래서 이 소스는
`TITLE_SIMILARITY_EXEMPT_SOURCES` 로 제외하고 고유 id 로만 구분합니다.

### 소스별 차단 현황 (2026-09-15 조사)
- **99.co**: 2026-08-15부터 GitHub 러너 IP에 403. 이 PC(가정용 회선)에서는 동일 요청이
  200으로 정상 응답함 → 데이터센터 IP만 막힌 것으로 확인. `scraper/daily_update.ps1`
  (Windows 작업 스케줄러, 매일 07:00)이 로컬에서 수집해 `js/live_data.js`를 커밋한다.
- **tempat-usaha.com**: GitHub 러너에서 첫 검색어부터 HTTP 403 (미처리 예외로 워크플로
  스텝이 크래시하던 버그가 있었음 — `scrape_business.py`의 `collect()`가 400만 처리하고
  다른 HTTP 오류는 그대로 raise 했다. 403/기타 오류도 "이 소스 중단"으로 처리하고 지금까지
  모은 후보로 계속 진행하도록 고침). 이 PC에서는 200으로 정상 응답 → 마찬가지로
  데이터센터 IP 차단이며 "물량 고갈"이 원인이 아니다. `daily_update.ps1`에 함께 포함해
  로컬 수집으로 우회한다.
- **OLX**: GitHub 러너에서는 전 검색어가 TimeoutError. 이 PC(가정용 회선, 데이터센터
  아님)에서 재현한 결과 `api.olx.co.id`, `www.olx.co.id` 모두 연결이 즉시 끊기거나
  (`ConnectionResetError`) 타임아웃되며, `curl`로도 동일하게 실패한다. 즉 GitHub 러너
  전용 차단이 아니라 이 네트워크/클라이언트 전반에 대한 차단(또는 API 자체 장애)으로
  보인다 — 데이터센터 IP 차단이라는 가설과 달라 **로컬 스케줄 우회가 통하지 않는다**.
  프록시 로테이션·TLS/지문 위장 등 차단 회피는 금지 규칙상 적용하지 않았다.
  현재는 워크플로에서 `continue-on-error`로 실패만 기록하고 넘어간다. 다른 네트워크
  (예: 인도네시아 현지 회선)에서 재확인하거나 OLX 측 상태가 바뀌면 재시도해볼 것.

### 인도웹 게시판 선정 (2026-08-11 실측)
`real_estate_mb`(28건/페이지)가 실제 매매·양도 글이 매일 올라오는 주력 게시판이고,
`biz_promo`에도 업체 양도 글이 섞여 올라옵니다. 기존 코드는 이 둘을 보지 않고
방치된 `real_estate`(4건)와 `market`만 봐서 수집이 **1건**에 그쳤습니다. 게시판을 넓히고,
당일 글의 `HH:MM` 날짜 형식을 파싱하게 고쳐 **8건**으로 늘었습니다.

상세 페이지에서 거래분류·주소·가격·건물형태·면적과 사진 URL을 함께 받아옵니다.
글쓴이 이름·전화·이메일·메신저 ID는 저장하지 않습니다(`MASK_RE`로 제거).

한인 사이트 추가 조사 결과: `haninpost.com`은 봇 요청에 응답이 끊기고,
`hankookin.com`은 본문이 비어 있는 JS 렌더링 사이트라 현재 수집 대상이 아닙니다.

## 사이트에 붙는 판정 (`enrich.py`)
예전에는 외국인 취득·운영 가능 판정을 텔레그램 발송할 때만 계산하고 버려서,
같은 매물을 사이트에서 봐도 한인이 인수할 수 있는 물건인지 알 수 없었습니다.
지금은 각 스크래퍼가 `js/*.js`를 쓰기 직전에 `enrich.annotate_all()`을 호출해
판정 결과를 매물 레코드에 남깁니다.

| 필드 | 내용 |
|---|---|
| `summaryKo` | 한글 요약 줄 목록 (`korean_brief`) |
| `foreignStatus` / `foreignReason` / `foreignSteps` | 가능·조건부·불가 + 사유 + 필요 절차 |
| `operability` / `operabilityReasons` / `operabilityTodos` | 운영가능·확인필요·부적합 + 근거 + 확인 항목 |
| `koreanEligible` | 위 둘의 결론. 사이트의 **"한인 인수 가능 매물만"** 체크박스가 이 값을 봅니다 |

`koreanEligible`은 '불가'와 '부적합'만 떨어뜨립니다. '조건부·확인필요'까지 버리면
실제로 볼 만한 물건이 거의 남지 않아서, 대신 사유와 절차를 함께 노출합니다.
판정 필드가 없는 구(舊) 수동 등록 매물은 필터에서 숨겨집니다 —
판정하지 않은 것을 가능으로 보여주면 필터의 의미가 없어지기 때문입니다.

### 부동산은 사업체와 다른 잣대로 본다 (2026-08-14)
`operability.py`의 '영업 실체' 규칙(매출·업력·직원 신호)을 부동산에도 그대로 적용하던
동안 99.co 매물 **153건 중 143건이 '부적합'**으로 떨어졌습니다. 루코 매매 글에 매출이나
직원 수가 적혀 있을 이유가 없으니 당연한 결과였고, 판정이 틀린 것이었습니다.
지금은 부동산에 대해 '실물을 특정하고 거래를 검토할 수 있는가'(가격·면적·좌표·증서 표기)를
묻는 별도 경로(`_classify_property`)를 씁니다. 같은 데이터에서 152건이 통과합니다.

### '조건부'가 사실상 전부 통과하던 문제 (2026-09-14)
Rp 4억짜리 카페·포차 자산 양도까지 '조건부'로 통과해 추천이 실제로는 적법하게 인수할 수
없는 매물로 채워졌습니다. 지금은 다음 기준을 씁니다.

| 거래 구조 | 판정 |
|---|---|
| 기존 법인 **지분 인수**(법인 매각) | 🟢 가능 — 새 PT PMA 불필요. PMA/PMDN·KBLI·법인 채무 실사 안내 |
| **자산 양도** + 인수가 < Rp 25억(신규 PT PMA 납입자본, BKPM 규정 2025-5) | 🔴 불가 — 현지인 명의 대여는 무효 |
| 자산 양도 + 가격 미표기 / Rp 25억 이상 | 🟡 조건부 |
| 편의점 가맹점(Alfamart·Indomaret), 초·중·고 정규학교 | 🔴 불가(외국인 투자 제한 업종) |

인도웹 수집도 함께 고쳤습니다: 게시판 분류(매매/임대)를 읽어 제목에 키워드가 없는 매매 글을
놓치지 않고, 공장·토지·아파트 글은 사업체가 아닌 부동산(`properti`)으로 판정하며,
'1 USD'·'월간 - …' 같은 자리채움·임대료 값은 매매가로 읽지 않습니다.

⚠️ 99.co 가 GitHub 러너에 403 을 반환해(2026-08-15~) 워크플로 전체가 중단되고 있었습니다.
99.co 스텝을 `continue-on-error` 로 바꿔 나머지 소스와 텔레그램 추천은 계속 돌게 했습니다.
이후 tempat-usaha.com도 같은 증상(데이터센터 IP 403)이 확인돼 마찬가지로
`continue-on-error`이며, 두 소스 모두 `scraper/daily_update.ps1`의 로컬 스케줄
수집으로 우회합니다. 자세한 소스별 차단 현황은 위 "소스별 차단 현황" 절 참고.

### 금액 5단계와 딜 구조 (`deal_tier.py`, 2026-09-19)
추천 메시지를 금액 5단계로 나눠 보내고, **매물이 없는 단계도 '적합 매물 없음'으로 적습니다** —
그 단계에 매물이 없다는 것 자체가 전략에 반영해야 하는 정보이기 때문입니다.

| 단계 | KRW | IDR 근사 | 제도상 의미 |
|---|---|---|---|
| 1단계 | ~₩1억 | ~Rp 1.1B | PMA 투자계획 Rp 100억 미달 — 단독 인수 구조 불성립 |
| 2단계 | ₩1~3억 | ~Rp 3.5B | 납입자본 Rp 25억이 인수가를 넘거나 비슷함(총 현금이 인수가보다 커짐) |
| 3단계 | ₩3~5억 | ~Rp 5.8B | 투자계획 미달 — 롤업·기존 PMA 전제 |
| 4단계 | ₩5~7억 | ~Rp 8.1B | 투자계획에 근접(운전자금 합산으로 충족 여지) |
| 5단계 | ₩7~10억 | ~Rp 11.6B | **투자계획 Rp 100억을 단독 충족할 수 있는 유일한 구간** |

딜 구조도 함께 표시합니다. 인허가가 법인 간 이전되지 않으므로 이 구분이 실행 난이도를 가릅니다.

- 🧾 **지분양수** — 법인 주식 인수. NIB·업종허가·거래처 계약이 함께 넘어온다. 대신 과거 세무·노무 우발부채도 함께 인수
- ⚠️ **자산양수** — 설비·영업권만 인수. 허가는 인수자가 전부 새로 받아야 한다(영업 공백 발생)
- 판정이 애매하면 **자산양수로 본다.** 공개 게시판의 `take over usaha` 는 사실상 전부 자산 양수라,
  이쪽으로 잘못 보는 것이 반대 방향 오판보다 덜 위험합니다.

기존 '예산 1~2억 2단 추천'은 발송 **순서**를 정하는 용도로 남아 있습니다(`_tier`).
섹션을 나누는 것은 5단계(`_tierIndex`)입니다.

### 0건일 때의 동작
기본값은 **탈락 사유 요약을 함께 보냅니다.** 아무것도 보내지 않으면 '매물이 없는 날'과
'파이프라인이 죽은 날'을 구분할 수 없고, 실제로 그 때문에 한 달간 추천이 끊긴 것을
아무도 몰랐던 적이 있습니다. 전달 경로만 시험할 때는 `--test-mode` 로 실행하면
`추천 매물 없음` 한 줄만 보냅니다.

### 예산 기준 2단 추천 (2026-09-17)
사용자 예산은 한국돈 1~2억(Rp 11.6억~23.2억, ₩1 = Rp 11.6 근사). 통과 매물을 두 묶음으로 보냅니다.

| 묶음 | 기준 | 안내 |
|---|---|---|
| **1차 최적** | 인수가 ₩1~2억 | 이 구간도 PT PMA 납입자본 Rp 25억(≈₩2.2억)을 먼저 넣고 그 안에서 인수·운전자금을 쓰는 구조. 총 현금 ₩2.2억+, 투자계획 Rp 100억(≈₩8.6억) 별도 |
| **2차 예산 밖** | ₩2억 초과 또는 가격 미표기 | 공동 투자·지분 일부 인수 등 다른 구조로 검토할 가치가 있는 것만 |

이를 위해 `foreign_eligibility` 의 자산양도 규칙을 한 단계 완화했습니다: 예전엔 Rp 25억 미만 자산양도를
전부 '불가'로 봤는데(₩1~2억 구간이 통째로 그 아래라 1차가 항상 0건), 지금은 **₩1억(Rp 11.6억) 이상은
'조건부'**로 열고 총 현금·투자계획 요건을 안내에 붙입니다. ₩1억 미만은 여전히 '불가'입니다.
현재 데이터(2026-09-17)에서 ₩1~2억 사업체 매물 7건은 전부 영업 실체가 '확인필요'라 1차 통과 0건입니다 —
규칙이 아니라 매물 글의 정보 부족이 원인입니다.

## 텔레그램 추천 - 3중 스크리닝
`telegram_recommend.py`는 아래 세 관문을 모두 통과한 매물만 발송합니다.

1. **운영 가능성** (`operability.py`) 🟩 운영가능 / 🟨 확인필요 / 🟥 부적합
   — 🟥는 발송 제외. 임대 글, 구인·가맹점 모집, 거래 종료, 365일 초과 게시,
   그리고 **영업 실체 신호(영업중 여부·매출·업력·직원)가 하나도 없는 글**이 여기서 걸립니다.
2. **외국인 취득 가능성** (`foreign_eligibility.py`) 🟢 가능 / 🟡 조건부 / 🔴 불가
   — 🔴는 발송 제외(Girik 미등기 토지, 외국인 투자 유보 업종).
   `--foreign-only-eligible` 로 🟢만 받을 수 있습니다.
3. **실재성** — 필수 필드·원본 링크·플레이스홀더 연락처·단위 오기재 가격 검증.

### 메시지에 담기는 내용

  섹션으로 나눠 제시. 인니어와 한국어 원문 모두에서 추출하며, 기계 번역은 하지 않습니다.

  거부, 퇴직금 승계, 숨은 채무 등)을 매물 조건에 해당할 때만 붙입니다.
